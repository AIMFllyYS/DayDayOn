# ADR-0027：Agent 裁判与分数库

- 状态：Proposed
- 日期：2026-11-05
- 决策人：负责人（待拍板），Kiro 起草
- 关联：Epic #33，子任务 #35、#36、#37、#38；规范 [checkin-modules.md](../conventions/checkin-modules.md)

## 背景

五个打卡板块的 Playbook 整页稿已经定稿：每次打卡提交后由 Agent 分析，给出达标 / 未达标结论、饮食的 5 分制评分和一份分析报告；未达标的记录照常保存，但不计入连续天数和排行。正式应用里打卡只是「填一条就算完成」，没有分数，也不区分有效与否。

需要决定三件事：结论由谁算、存在哪里、Agent 怎么接进来。

## 面临的选项

1. **模型直接给结论**：让模型输出 `isValid` 和分数，服务端照存。
2. **模型给事实，规则给结论**：模型（带工具、可联网）只负责估算规则需要的数（每道菜的营养、运动 MET、笔记是否有实质），由纯函数按用户的阈值算出结论；服务端入库时用同一个纯函数重算。
3. **只用规则，不用模型**：前端直接按阈值判定。

## 决定

选 2。

- 判据写在 `src/features/referee/rules/` 的纯函数里，前后端共用：前端用于即时预览，服务端在创建打卡时重算并以重算结果入库。
- Agent 用 `ToolLoopAgent` 流式运行，最后必须调用 `submitVerdict(facts)`；`submitVerdict` 的入参是该板块的事实 schema，执行时调用纯函数得到结论。
- 分数库：`checkins` 加 `score`、`is_valid`、`verdict`（jsonb）三列；`profiles` 加 `referee_tier`；`goals` 加 `referee_rules`（jsonb）与 `deadline_date`。老数据 `is_valid` 默认 true。
- 统计（进度、完成度、连续天数、排行、好友动态）只在 `stats.ts` 过滤 `is_valid = false`。
- AI 不可用（暂停、额度不足、模型没调 `submitVerdict`）时降级为离线判定，结论里标 `offline: true`，打卡不因此失败。

## 理由

- 同一份输入永远得出同一个结论，可以写单测；阈值改了不用改 prompt。
- 模型擅长的是估算和判断文字内容，不擅长稳定地按阈值比较；把比较交给代码，模型的错只会影响事实，用户在草稿里能看到并修改。
- 服务端重算后，前端伪造 `isValid` 没有意义；伪造事实等同于手动乱填，和现在的手动打卡风险相同。
- 流式 + 工具调用让抽屉里的「思考 → 联网 → 估算」是真实发生的步骤，复用 Agent 对话已经验证过的账本、映射层和 `<AgentTurn>`。

## 放弃了什么

- 选项 1：结论不可复现，阈值改动要改 prompt，且用户可以通过改请求体绕过。
- 选项 3：饮食评分离不开营养估算，纯规则做不到 Playbook 要求的逐菜分析。
- 不做「打卡后再异步裁判」：结论必须在用户确认前给出，才能让用户选择「补足再打」或「仅保存记录」。

## 何时重审

- 单次裁判的平均费用超过 0.02 元，或 P95 耗时超过 15 秒。
- 需要支持「先保存、事后补裁判」（例如离线打卡同步）。
