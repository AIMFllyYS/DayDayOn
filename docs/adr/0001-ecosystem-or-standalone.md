# ADR-0001：接入 1037Solo 生态，还是独立部署

> 状态：Accepted（采纳方案 B，独立部署） · 日期：2026-10-31 · 决策人：项目负责人（AI 提供分析）
> 原路径：`docs/designs/adr-0001-ecosystem-or-standalone.md`，2026-10-31 按 demo-init 新版迁入 `docs/adr/`，编号与正文不变。
> 本仓库是公开仓库，1037Solo 生态的内部细节（服务地址、部署脚本、数据库结构）不写在这里。

## 1. 背景

- 定位：RootSolo 生态未来的一环，目前是和朋友一起用的试点，优先快速从 0 到 1 迭代；短期内负责人没有时间维护跨项目集成。
- 已定：部署方式与 1037Solo 系列一致（GitHub Actions 构建制品 → 受限 SSH 部署 → PM2）。

## 2. 关键事实（2026-10-31 实测）

| 项 | 结果 |
|---|---|
| 服务器区域 | 阿里云武汉（`cn-wuhan-lr`） |
| 服务器 → 生态数据库（Supabase，新加坡） | TCP 建连 77–155ms；一次 HTTPS 请求 0.26–0.36s |
| 服务器本机 PostgreSQL | 同机回环，亚毫秒 |
| 生态账号规则 | 昵称与头像只能在统一账号中心修改，产品不能写入 |
| 生态先例 | 已有产品采用"统一登录 + 本机业务数据库"的混合方式 |

## 3. 三个方案

- **A 全面接入**：统一登录 + 统一钱包 + 生态 Supabase 存业务数据
- **B 独立**：Better Auth + 阿里云邮件推送 + 本机 Docker PG
- **C 混合**：统一登录 + 统一钱包 + 本机 Docker PG 存业务数据

| 维度 | A | B | C |
|---|---|---|---|
| 登录、注册、找回密码 | 现成 | 自建（约半天） | 现成 |
| 新人引导里设置昵称头像 | 不行 | 可以 | 不行 |
| 登录页风格 | 统一页面 | 自己设计 | 统一页面 |
| 业务数据查询延迟 | 每次跨境 0.1–0.3s | 本机 | 本机 |
| 表结构迭代 | 在生产共享库上人工迁移 | 迁移跟代码走 | 同 B |
| AI 额度 | 统一钱包 | 自建 | 统一钱包 |
| 需要改动其他生产仓库 | 是 | 否 | 是 |
| 本地开发依赖 | 需启动生态账号服务 | 只要 Docker PG | 同 A |
| APK / Kotlin 登录 | OAuth 2.1 + PKCE，需登记客户端 | Bearer token | 同 A |
| 以后并入生态 | 已在 | 约 2 天迁移 | 基本不用 |

## 4. 决策

采用 **B**，作为独立项目运行，短期不迁入生态。

理由：

1. 试点期最影响迭代速度的是数据库位置和迁移方式，B 用本机 PG，迁移随代码走。
2. 不需要改动生态的其他生产仓库，负责人不在时也不会被跨项目发布卡住。
3. 新人引导可以按产品设计设置昵称头像，登录页也能统一成治愈风。

为了以后并入生态时成本低，代码遵守这些约定：

1. 用户 ID 用 UUID，业务表的 `user_id` 不外键到认证表。
2. `src/server/auth/` 只对外暴露 `requireUser()`，返回 `user_id`、`email`、`name`、`avatar_url`。
3. API 错误体用 `{ "code": "...", "detail": "..." }`。
4. AI 每次调用记录 token 用量和幂等键，金额用微元（与生态单位一致）。

## 5. 采纳时的修订

- 部署目录放 `/www/wwwroot/daydayon`，与 1037Solo 的目录、部署脚本、PM2 服务完全隔离。方案见 [deploy-aliyun-ecs.md](../ops/deploy-aliyun-ecs.md)。
- 图片解析后只存文本，图片永不落盘。
- 账号、邮件、额度、风控、后台见 [ADR-0002](./0002-account-quota-risk.md)。

## 6. 何时重审

> 2026-10-31 按 ADR 模板补充，正文其余部分不变。

- 负责人决定把 DayDayOn 并入 RootSolo 生态，或需要和 1037Solo 产品共用登录、额度时。
- 生态的统一账号允许产品写入昵称和头像时（第 3 节方案 A / C 的主要缺点消失）。
- 用户规模超出"朋友试点"，需要统一运维时。
